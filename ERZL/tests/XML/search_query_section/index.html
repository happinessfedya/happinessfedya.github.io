    Тесты SearchQuerySection

    Эта страница показывает тесты из общего test-файла. Команда, на которой основаны сценарии:

    python -m pytest -vv -s tests/xml/test_search_query_section.py

    Флаг -s здесь не добавляет пользовательской печати: модуль не выводит свои сценарии, поэтому в pytest видны только имена тестов и статусы PASSED. Ниже раскрыто, какие именно search XML-сценарии, controlled retry-ошибки и архитектурные ограничения стоят за этими статусами.

    Докстринг модуля

    Тесты для `XML.xml_builder.SearchQuerySection`.

Модуль проверяет контракт секции `searchQuery`: построение блоков
`searchQuery/code/value`, поведение на пустых и повторяющихся поисковых парах,
контролируемые retry-сценарии и архитектурную изоляцию от create-flow.

Файл нужен для фиксации того, что `SearchQuerySection` отвечает только за
формирование XML-поисковых узлов и не смешивает эту задачу с transport- или
create-логикой.

    Исходный код больше не вынесен в один общий блок сверху. Ниже у каждого сценария есть отдельный раскрывающийся блок с кодом именно того теста, который документируется.

    Зачем этот класс

    SearchQuerySection живет в XML-слое и отвечает только за построение блоков searchQuery внутри запроса поиска персоны. Класс берет:

    • parent, у которого уже есть namespace;
    • XMLBuilderSearchDTO, содержащий search_pairs и RequestType.

    На выходе он:

    • создает по одному searchQuery на каждую пару из search_pairs;
    • внутри каждого блока создает code и value;
    • использует namespace родительского request-элемента.

    Этот класс не:

    • не выбирает тип операции поиска;
    • не валидирует бизнес-смысл конкретных code;
    • не интерпретирует transport или create-flow;
    • не скрывает ошибки кривой формы search_pairs;
    • не зависит от RequestType при одинаковых search_pairs.

    Этот тест важен, потому что RequestType живет в DTO, но сама секция не должна зависеть от него. Если поисковые пары одинаковые, XML-фрагмент должен быть идентичным независимо от MOSCOW или NONRESIDENT.
