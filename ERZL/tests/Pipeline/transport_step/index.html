    Тесты TransportStep

    Эта страница показывает тесты из общего test-файла. Команда, на которой основаны сценарии:

    python -m pytest -vv -s tests/pipeline/test_transport_step.py

    Флаг -s здесь не добавляет пользовательской печати: модуль не выводит свои сценарии, поэтому в pytest видны только имена тестов и статусы PASSED. Ниже раскрыто, какие именно async-сценарии, controlled fail-ветки и архитектурные ограничения стоят за этими статусами.

    Докстринг модуля

    Тесты для `Pipeline.pipeline_protocols.TransportStep`.

Модуль фиксирует async-контракт транспортного шага: controlled fail-ветки,
делегирование lifecycle в transport и изоляцию от source/XML parsing логики.

Тесты нужны для защиты шага, который отправляет подготовленный XML через
transport, записывает ответ в context через adapter и не смешивает эту логику
с source-, XML-building- или parser-ответственностью.

    Исходный код больше не вынесен в один общий блок сверху. Ниже у каждого сценария есть отдельный раскрывающийся блок с кодом именно того теста, который документируется.

    Зачем этот класс

    TransportStep живет в Pipeline-слое и отвечает только за границу отправки готового XML и записи сырого ответа обратно в context. Он связывает две зависимости:

    • transport.send(xml_bytes) отправляет XML и возвращает TransportResponseDTO;
    • trans_adapter.answer_bytes_to_ctx(resp, ctx) пишет resp.output_bytes в ctx.response_bytes.

    Этот шаг:

    • читает ctx.xml_bytes;
    • как async context manager делегирует __aenter__ и __aexit__ во внутренний transport;
    • возвращает StepRslt.ok(SUCCES) на штатном пути;
    • controlled fail-сценарии переводит в StepRslt.stop(FAIL).

    Этот шаг не:

    • не строит XML и не знает о builder-ошибках;
    • не знает ничего о AttemptId, SourceData и логике попыток;
    • не парсит ответ;
    • не скрывает неожиданные runtime-ошибки transport-а и adapter-а.
