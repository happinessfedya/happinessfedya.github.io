    Тесты AnswerDecisionStep

    Эта страница показывает тесты из общего test-файла. Команда, на которой основаны сценарии:

    python -m pytest -vv -s tests/pipeline/test_answer_decision_step.py

    Флаг -s здесь не добавляет пользовательской печати: модуль не выводит свои сценарии, поэтому в pytest видны только имена тестов и статусы PASSED. Ниже раскрыто, какие именно результаты, ошибки и архитектурные ограничения стоят за этими статусами.

    Докстринг модуля

    Тесты для `AnswerDecisionStep`.

Модуль фиксирует контракт шага разбора XML-ответа: проброс `response_bytes` в
сервис разбора, ветвление по controlled exceptions и строгую изоляцию от
transport/source-логики.

Тесты нужны для защиты шага, который получает результат transport-слоя,
передает его в сервис разбора и записывает итог в context, не смешивая эту
логику с source- или transport-ответственностью.

    Исходный код больше не вынесен в один общий блок сверху. Ниже у каждого сценария есть отдельный раскрывающийся блок с кодом именно того теста, который документируется.

    Зачем этот класс

    AnswerDecisionStep живет в Pipeline-слое и отвечает за последний шаг работы с сырым XML-ответом. Он связывает две зависимости:

    • get_answer.get_rslt_container(response_bytes, required_fields, optional_fields) разбирает XML и возвращает XMLRsltContainer либо controlled exception;
    • adapter.rslt_container_to_ctx(ctx, rslt) переносит нормализованный результат в context.

    Этот шаг:

    • берет response_bytes из context;
    • передает их parser-service вместе с required и optional полями;
    • превращает controlled exceptions в StepRslt.stop(...);
    • на успешном пути записывает XMLRsltContainer в context.rslt_container.

    Этот шаг не:

    • не занимается низкоуровневым XML-parsing сам;
    • не знает о transport-отправке и не работает с HTTP;
    • не управляет попытками и source-данными;
    • не скрывает неожиданные runtime-ошибки collaborators.
