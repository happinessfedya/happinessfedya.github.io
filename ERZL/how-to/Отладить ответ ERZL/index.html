    Отладить ответ ERZL

    Порядок действий

    Ответ ERZL удобно отлаживать по одной и той же последовательности:

    1. проверить, какой XML ушёл в ERZL;
    2. проверить, что вернул транспорт;
    3. посмотреть решение шага разбора ответа;
    4. проверить, что попало в rslt_container;
    5. проверить, появился ли ERZL_id;
    6. проверить, был ли переход в create-flow.

    Итоговая цепочка выглядит так:

    xml_bytes
-> response_bytes
-> AnswerDecisionStep
-> rslt_container
-> ERZL_id / create_flags

    1. Проверить XML, который ушёл в ERZL

    Файл сборки XML: XML/xml_builder.py
    Файл orchestration: Orchestrator/Orchestrator.py

    После шага построения XML в контекст кладётся:

    ctx.xml_bytes

    Что смотреть

    • есть ли вообще xml_bytes;
    • соответствует ли XML текущей попытке;
    • содержит ли XML нужные поля из ctx.DataAttemptStr;
    • соответствует ли RequestType текущему ctx.PersonType.

    Пример

    Если сейчас идёт search-попытка по snils, то перед отправкой в контексте должны быть:

    ctx.AttemptId == 0
ctx.DataAttemptStr == (PersonFields.SNILS,)
ctx.PersonType == AllXMLFields.ERZL.OperationsStr.FindPersonsType.MOSCOW
ctx.xml_bytes is not None

    Если на этом этапе xml_bytes пустой, проблема находится до транспорта:

    • в выборе полей попытки;
    • в адаптации SourceData -> XMLKVPairs;
    • в XML builder.

    2. Проверить сырой ответ транспорта

    Файл транспорта: XML/xml_transport.py
    Файл адаптера транспорта: Adapters/Adapters.py

    После отправки XML в контекст кладётся:

    ctx.response_bytes

    Что смотреть

    • есть ли response_bytes;
    • это валидный XML или пустой ответ;
    • есть ли в ответе Fault;
    • соответствует ли response тому запросу, который был отправлен.

    Пример

    После успешного transport-шага:

    ctx.response_bytes is not None

    Если response_bytes пустой или не похож на XML, проблема находится в транспортном слое.

    Если response_bytes заполнен, но дальше ничего не находится, проблема уже в разборе ответа или в бизнес-решении после разбора.

    3. Посмотреть решение шага разбора ответа

    Файл шага разбора: Pipeline/pipeline_protocols.py
    Файл enum решений: Pipeline/pipeline_core_types.py

    Ответ разбирается через:

    self._get_answer.xml_rslt_to_ctx(ctx, required_fields, optional_fields)

    Этот шаг возвращает одно из решений:

    • CONTINUE
    • RETRY
    • REBUILD_AND_RETRY
    • SKIP_CONTEXT
    • ABORT

    Как читать решения

    CONTINUE

    XML успешно разобран, и результат уже положен в:

    ctx.rslt_container

    RETRY

    Ответ можно попробовать распарсить ещё раз без пересборки XML.

    REBUILD_AND_RETRY

    Перед повтором нужно заново собрать XML и снова отправить запрос.

    SKIP_CONTEXT

    Ответ не содержит обязательных данных для текущего сценария.

    ABORT

    Пайплайн для текущего контекста нужно остановить.

    4. Проверить rslt_container

    Файл разбора XML: XML/xml_getAnswer.py
    Файл merge результата в context: Adapters/Adapters.py

    После успешного разбора шаг складывает результат в:

    ctx.rslt_container

    Внутри контейнера есть два основных блока:

    • ctx.rslt_container.result
    • ctx.rslt_container.mistakes

    Что смотреть сначала

    Успешные данные

    ctx.rslt_container.result

    Это список DTO по response-контейнерам.

    Пример:

    ctx.rslt_container.result[0].response_name
ctx.rslt_container.result[0].container

    Ошибки ERZL

    ctx.rslt_container.mistakes

    Если ERZL вернул читаемую fault-ошибку, она попадёт именно сюда.

    Пример проверки search-ответа

    Для поиска персоны orchestrator ищет в result поле:

    AllXMLFields.ERZL.Response.FindPerson.SearchPerson.PERSON_ID

    То есть фактически нужно проверить, есть ли в контейнере что-то такого вида:

    for rslt in ctx.rslt_container.result:
    for field in rslt.container:
        print(field.container_name, field.container_val)

    Если там есть:

    id 123456

    значит PERSON_ID найден.

    5. Проверить, появился ли ERZL_id

    Файл orchestration: Orchestrator/Orchestrator.py
    Файл ERZL-адаптера: Adapters/Adapters.py

    После search-разбора orchestrator проходит по ctx.rslt_container.result и ищет:

    field.container_name == AllXMLFields.ERZL.Response.FindPerson.SearchPerson.PERSON_ID.value

    Если поле найдено, orchestrator выполняет:

    self._erzl_adapter.set_ERZL_id(ctx, field.container_val)

    Что проверить

    ctx.ERZL_id

    Пример

    После удачного поиска:

    ctx.ERZL_id == "123456"

    Если в rslt_container.result поле уже есть, а ctx.ERZL_id всё ещё None, проблема находится в логике ветвления после разбора.

    6. Проверить переход в create-flow

    Файл orchestration: Orchestrator/Orchestrator.py
    Файл флагов контекста: Source/source_core_types.py

    Если после search-ответа PERSON_ID не найден, orchestrator переводит контекст в create-flow:

    self._erzl_adapter.set_need_create(ctx, True)

    Что проверить

    ctx.create_flags.need_create

    Пример

    Если поиск ничего не дал:

    ctx.ERZL_id is None
ctx.create_flags.need_create is True

    Это означает, что search-ветка завершилась и начнётся создание персоны.

    7. Как отлаживать create-base ответ

    После перехода в create-flow первым разбирается ответ создания базовой персоны.

    В этом месте orchestrator ждёт поле:

    AllXMLFields.ERZL.Response.CreatePerson.Base.NONRES_ID

    Что проверить

    1. есть ли ctx.response_bytes после create-base запроса;
    2. попал ли nonresId в ctx.rslt_container.result;
    3. записался ли он в:
    ctx.ERZL_id

    Пример

    После успешного create-base:

    ctx.ERZL_id is not None
ctx.create_flags.good_create_base is True

    Если response_bytes есть, но nonresId не найден, значит проблема в содержимом ответа или в наборе обязательных полей для разбора.

    8. Как читать итоговое состояние контекста

    После одного полного цикла обработки полезно смотреть контекст в таком порядке:

    1. ctx.DataAttemptStr

    Показывает, какие поля реально были использованы в текущей попытке.

    2. ctx.xml_bytes

    Показывает, какой XML реально ушёл.

    3. ctx.response_bytes

    Показывает, что реально вернул ERZL.

    4. ctx.rslt_container.result

    Показывает, что удалось извлечь из ответа.

    5. ctx.rslt_container.mistakes

    Показывает ошибки, которые ERZL вернул в читаемом виде.

    6. ctx.ERZL_id

    Показывает, найден или создан идентификатор персоны.

    7. ctx.create_flags

    Показывает, был ли переход к созданию и какие create-операции завершились успешно.

    9. Готовые сценарии проверки

    Сценарий 1. Ответ пришёл, но персона не найдена

    Проверьте по порядку:

    ctx.response_bytes is not None
ctx.rslt_container.result
ctx.ERZL_id
ctx.create_flags.need_create

    Ожидаемая картина:

    ctx.response_bytes is not None
ctx.ERZL_id is None
ctx.create_flags.need_create is True

    Сценарий 2. Ответ пришёл, но rslt_container пустой

    Проверьте:

    1. что response_bytes действительно содержит XML;
    2. что AnswerDecisionStep вернул CONTINUE, а не SKIP_CONTEXT;
    3. что в required_fields переданы правильные XML-поля.

    Сценарий 3. PERSON_ID есть в XML, но ERZL_id пустой

    Проверьте:

    1. что в ctx.rslt_container.result действительно есть поле с именем:
    AllXMLFields.ERZL.Response.FindPerson.SearchPerson.PERSON_ID.value
    1. что после разбора отработала ветка:
    GetAnswerDecision_StrEnum.CONTINUE
    1. что orchestrator дошёл до вызова:
    self._erzl_adapter.set_ERZL_id(ctx, field.container_val)

    Сценарий 4. После create-base не появился ERZL_id

    Проверьте:

    ctx.response_bytes
ctx.rslt_container.result
ctx.ERZL_id
ctx.create_flags.good_create_base

    Ожидаемая картина для успешного create-base:

    ctx.ERZL_id is not None
ctx.create_flags.good_create_base is True
