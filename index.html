    Общая структура проекта

    Структура модулей

    • Общие модули (Source, DataSelector, XMLBuilder и прочее) должны быть максимально простыми для их универсальности. Не должны совершать никаких доменных преобразований данных. Только технические преобразования. Не служат фильтром данных за исключением проверок на битые данные. Например: Source просто отдает данные из источника. Adapter отвечает за преобразование данных таким образом, который подойдет для дальнейшей работы с пайплайном.
    • Адаптеры - Отвечают за изменение данных, как в примере выше. В т.ч. за изменение контекста. Изменением контекста считается также и присваивание переменной контексту (adapter.put_bytes()). В проекте никогда не должно быть изменения контекста не через адаптер (context.attempt_id + 1; adapter.attempt_plus_one()).
    • Пайплайн - Служит объединением общих модулей и адаптеров в шаги. Шагом считается микро-задача, финалом которой считается любое изменение контекста. Возвращать шаг должен StepRslt.ok\error\abort с StepRslt.decision, соответствующим конкретному шагу. Набор decision прописывается внутри protocols_core_types.py
    • Оркестратор - Служит объединением шагов, где в соответствии с разным StepRslt.decision определяется какое будет следующее действие. Здесь зашита исключительно бизнес логика.

    Структура типов данных

    Проект использует статическую типизацию Python (type hints + mypy) с применением generics, Protocol (структурной типизации) и типизированных DTO для построения модульного пайплайна.
    *_core_types.py - В подобных файлах объявляются и хранятся типы данных, кроме тех, которые исползуются в моменте для конкретного метода и не предвидится использований этого же типа. В таком случае объявляем прямо над методотом\классом, где используется этот тип.

    Возвращаемые данные - Все возвращаемые типы должны быть четко прописаны как @dataclass.

    Анти-паттерны - В коде не должно быть\должен быть минимум непонятно откуда взятых str, int и т.д. Все они должны быть отдельно объявлены и использоваться через ссылку на объявление.

    Документация проекта

    Документация описывает текущую архитектуру модульного интеграционного пайплайна и правила его расширения.

    Сейчас в репозитории реализован ERZL-пайплайн: - источник читает строки из XLSM; - adapter переводит данные в канонические поля; - создаётся ERZL_Context; - pipeline steps подготавливают попытки, XML и ответ; - orchestrator управляет search-flow и create-flow.

    Как читать эту документацию

    • Если нужно понять систему целиком — начни с architecture/overview.md.
    • Если нужно понять жизненный цикл context — читай architecture/context-lifecycle.md.
    • Если нужно изменить поведение пайплайна — смотри how-to/.
    • Если нужен точный контракт типов, шагов или конфигов — смотри reference/.
    • Если нужно понять причины архитектурных решений — смотри adr/.

    Страницы документации

    architecture/overview.md

    Главная архитектурная страница проекта.

    Для чего нужна: - объясняет общую структуру системы; - показывает границы ответственности между Source, Adapters, ContextFactory, DataSelector, Pipeline steps, XML-layer и Orchestrator; - помогает понять, в каком слое должна жить новая логика.

    Когда читать: - при первом знакомстве с проектом; - перед архитектурными изменениями; - если непонятно, куда добавлять новый код.

    architecture/context-lifecycle.md

    Описание жизненного цикла ERZL_Context.

    Для чего нужна: - показывает, кто и когда создаёт context; - объясняет, какие поля context заполняются на разных этапах; - фиксирует, какие модули имеют право изменять конкретные поля.

    Когда читать: - если меняется состав context; - если нужно понять, откуда взялось текущее состояние; - если есть риск смешать ответственность orchestrator и adapter.

    architecture/pipeline-flow.md

    Подробное описание выполнения одного context.

    Для чего нужна: - показывает последовательность шагов search-flow; - описывает переход в create-flow; - объясняет retry-логику и ветвления orchestrator.

    Когда читать: - если нужно понять реальный runtime flow; - если меняется логика попыток, поиска или создания.

    Справка по основным DTO, dataclass и enum.

    Для чего нужна: - фиксирует ключевые типы проекта; - помогает быстро понять, какой объект что содержит; - служит опорой для типизации и docstring.

    Когда читать: - если нужно быстро посмотреть структуру DTO; - если добавляется новый тип; - если меняется контракт между слоями.

    reference/config-erzl.md

    Справка по bootstrap-конфигу ERZL.

    Когда читать: - если меняется конфиг; - если добавляется новый профиль; - если нужно понять, откуда берутся зависимости в bootstrap.

    Для чего нужна: - описывает, что принимает и возвращает каждый step; - фиксирует, какие step-result и decision используются; - помогает не смешивать step-логику и orchestrator-логику.

    Когда читать: - если меняется конкретный step; - если нужно добавить новый шаг; - если нужно понять контракты StepRslt и decision enum.

    reference/xml-layer.md
